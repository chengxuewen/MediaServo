# SDP Negotiation Audit: Host Build Form + the Bitrate Chain (2026-08-12)

> Related: [`mediasoup-client.md`](mediasoup-client.md) (official client architecture comparison), [`webrtc-w3c-alignment.md`](webrtc-w3c-alignment.md) (the D214/D216 rework), `conventions.md` C18 (official-usage-first), PIT-65 (the hand-rolled negotiation lesson)
> Conclusion adopted: **options A+C** (complete the self-built offer's transport-cc/rtcp-fb + fix the bitrate_kbps semantics) → implementation plan in `docs/plans/sfu-negotiation-completion/plan.md`

## 1. Conclusion Summary

1. **The negotiation APIs are now fully standard** (PIT-65 remediation done): `setRemoteDescription → add_track → createAnswer → setLocalDescription` (the SFU path) / `createOffer → setLocalDescription` (the P2P path); produce parameters are derived via the official `get_sending_rtp_parameters` path.
2. **The remote SDP text is still hand-assembled by the host** (`sfu_media::build_remote_sdp`) — this is inevitable in the mediasoup architecture (the server never produces SDP; signaling carries only `iceParameters/dtlsParameters/iceCandidates` JSON); the official SDK (libmediasoupclient's `RemoteSdp`) likewise builds its own SDP, only it **builds the answer rather than the peer's offer** (the client-offer model is a follow-up purity item, option B).
3. **The real gap vs official = the self-built offer's content is simplified** (single codec, no rtcp-fb, no extmap, add_track with a non-W3C signature), not "negotiation semantics errors".
4. **The bitrate-setting chain has a systematic break**: the self-built offer has no extmap → transport-cc never negotiated → BWE feedback broken → `max_bitrate` never reaches target and `min_bitrate` degrades from best-effort to a de-facto fixed rate; `bitrate_kbps` (default 2000) feeds only the GStreamer capture pipeline and has zero effect on the WebRTC encoder (a dead parameter).

## 2. The Host's SDP Build Form (current implementation, main.rs:289-429)

```
① Build the peer's offer:  sfu_media::build_remote_sdp()  ← hand string assembly (mimicking a server ICE-Lite offer)
② set_remote_description(offer)                    ← standard W3C API
③ add_track("video")                               ← non-W3C signature (no track / no sendEncodings)
④ create_answer() + set_local_description(answer)  ← standard W3C API (the answer is generated by libwebrtc)
⑤ produce parameters: get_sending_rtp_parameters() ← the official derivation path, not hand-made
   → build_produce_rtp_parameters_from_rtp()       ← JSON-serialization adaptation only
```

Self-built remote offer content (`sfu_media.rs:29-86`):

| Element | Value | Notes |
|------|-----|------|
| Session-level | `a=ice-lite` / `a=setup:actpass` / `a=group:BUNDLE video` | Matches the mediasoup WebRtcTransport (ICE-Lite, DTLS role auto) |
| Direction | `a=recvonly` | The server (offerer) is the receiver; correct |
| codec | Single-codec rtpmap/fmtp (h264=101/vp8=96/vp9=99/av1=97) | Determined by `config.encoder.codec`; auto=VP8 |
| candidates | Signaling `iceCandidates` inserted into the media section (after the m= line) | PIT-48: session-level candidates are ignored by libwebrtc |
| **Missing** | **`a=rtcp-fb` (nack/pli/fir)** | impact ↓ section 5 |
| **Missing** | **`a=extmap` (transport-cc/abs-capture-time)** | impact ↓ section 5 |

## 3. Official Comparison (mediasoup-client.md §2/§4)

| # | Official (libmediasoupclient / mediasoup-client JS) | MediaServo Host state |
|---|------|------|
| Role | client = the **offerer**: `addTransceiver(sendonly) → createOffer → setLocalDescription(offer)` | client = the **answerer**: builds the peer's offer itself → `setRemoteDescription` |
| Self-built side | the **answer is built by the SDK** (`RemoteSdp::Send()`, RemoteSdp.cpp:157-185) → `setRemoteDescription(answer)` | the **offer is built by the app layer** (`build_remote_sdp`) → negotiation; the answer is generated by libwebrtc |
| Parameter source | ssrc/PT/fmtp derived from the offer (`getSendingRtpParameters`) | `get_sending_rtp_parameters()` (same nature, the official path) |
| server | only receives rtpParameters, **never returns SDP** | same (`signaling.rs` contains no SDP code at all, verified) |

The rejected old directions (the 5 rows of the PIT-65/§4 table): bypassing negotiation (role reversal, hand-hardcoded produce parameters, hand-parsing the answer's ssrc) — **all eliminated**.

## 4. Remaining Gaps (self-built peer offer vs a createOffer-generated offer)

| Gap | Impact | Severity | Status |
|------|------|--------|:----:|
| The self-built offer has **no `a=rtcp-fb`** (nack/pli/fir) | NACK retransmission and PLI feedback may be unnegotiated; degraded quality on lossy networks | medium | planned T1 |
| The self-built offer has **no extmap** (transport-cc/abs-capture-time) | **The BWE feedback chain breaks** (the core of section 5); browser-side latency stats missing | **high** | planned T1 |
| **Single-codec offer** (config pins one) | Only one of the router's 5-codec capability set is negotiated at a time; auto=VP8 | low | accepted as-is |
| `add_track("video")` with a non-W3C signature (§4 legacy) | No sendEncodings → no simulcast/multi-encoding | low | accepted as-is |

## 5. The Bitrate Chain Panorama (2026-08-12 analysis)

```
host.conf encoder.bitrate_kbps=2000 ──→ Pipeline::new (the GStreamer capture pipeline, pipeline.rs:81)
                                    └── the SFU main path (test_pattern→WebRtcTrackSink→libwebrtc encoding)
                                          → bitrate_kbps is a dead parameter (misleading; planned T3)
host.conf encoder.min/max_bitrate_kbps ──→ main.rs:361 set_encoding_bitrate(min_bps, max_bps)
  → webrtc_sys.rs:669 SetParameters(enc.min/max_bitrate_bps) → libwebrtc ReconfigureEncoder
  → produce rtpParameters.encodings[0].maxBitrate (build_produce reflection, sfu_media.rs:124)
  → mediasoup RtpEncodingParameters.max_bitrate (mediasoup-0.24.1 rtp_parameters.rs:117/158, parsed and stored correctly)
```

Verdict per link:

| Link | Status | Notes |
|------|:----:|------|
| Config validation | ✅ | `validate_bitrate()` (main.rs:76, config.rs:184): min>0, min<max, preventing double libwebrtc failure |
| Call timing | ✅ | After negotiation, before the first frame (main.rs:361), before ReconfigureEncoder takes effect, called once only |
| libwebrtc semantics | ✅ | max = hard ceiling (reliable); min = the allocation-layer floor (the encoder's safety net when BWE drops below it, best-effort) |
| Server side | ✅ | mediasoup is the **receiver**; maxBitrate is only stored/offered to consumers in negotiation (rtp_parameters.rs:351/380); no `maxIncomingBitrate` → never caps the rate |
| **The BWE feedback chain** | ❌ | Neither transport-cc nor REMB negotiated (next section) |

## 6. The Broken BWE Feedback Chain (the core problem)

```
The self-built offer has no extmap → the answer has no transport-cc extension (RFC 8285: an answer may only accept a subset of the offer's set)
  → RTP packets carry no transport-cc header extension
  → produce headerExtensions=[] (hardcoded at sfu_media.rs:131)
  → mediasoup has no transport-cc context, generates/forwards no feedback to the host
  → libwebrtc's BWE has no input at all (neither transport-cc nor REMB; rtcp-fb also unnegotiated)
  → the encode target = clamp(initial estimate, min, max) — the initial estimate defaults to ~300kbps (the webrtc-sys default needs empirical confirmation)
```

Consequences:

1. **max_bitrate=2000k is effectively decorative** — it only truncates the ceiling; the BWE stays at its initial value → the actual rate ≈300k~1M, never reaching the target
2. **min_bitrate degrades from best-effort** — without feedback the BWE neither rises nor falls; min becomes the encoder's de-facto fixed rate; a high min under weak network = constant high-rate congestion with no adaptivity
3. **bitrate_kbps=2000 (default) has zero effect on the WebRTC encoder** — under the default config (min/max both None) libwebrtc has no bitrate hint at all; the actual rate is neither guaranteed nor controllable
4. **Evidence gap**: earlier stats-panel verification covered encoder_implementation/fps/resolution but never recorded the actual rate — whether the chain breaks needs live confirmation (the browser consume side's bytesReceived delta)

## 7. Option Comparison & Decision (A+C adopted)

| Option | Content | Pros | Cons | Decision |
|------|------|------|------|:----:|
| **A. Complete the self-built offer** | `build_remote_sdp` gains `a=extmap` (transport-cc/abs-capture-time) + `a=rtcp-fb` (nack/pli); produce headerExtensions derived from the negotiation result | Minimal change (one function); fixes PLI/NACK and BWE at once; mediasoup automatically gains the transport-cc context | Still not the official client-offer model | **Adopted** |
| **B. Move to the official client-offer model** | `addTransceiver(sendonly)→createOffer→build the answer ourselves` | createOffer naturally carries complete extmap/rtcp-fb; once and for all; fully aligned with libmediasoupclient | A large change (host + browser ends + pushing the self-built answer down into the SDK); full regression | a later purity item |
| **C. Fix the bitrate_kbps semantics** | Make bitrate_kbps the source of the min/max defaults or mark it deprecated; update the host.conf comments | Removes the misleading | Doesn't fix the broken BWE chain | **Adopted** |
